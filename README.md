# Vesper

A fast, bloat-free screen recorder for desktop and gaming, written in Rust. An alternative to OBS Studio focused on recording.

## Goals

- Zero-copy pipeline: frames never touch system RAM.
- Under 1% CPU at 1440p144 / 4K60, no dropped frames.
- A clean, modern UI (Slint).

## Architecture (Linux / Wayland first)

1. **Capture**: `xdg-desktop-portal` ScreenCast (`ashpd`) to a PipeWire stream (`pipewire`) using DMA-BUF. Cursor as metadata.
   **Game capture** (Vulkan, incl. Proton and 32-bit games; native OpenGL games through `vesper-gl`): an implicit Vulkan layer (`vesper-vklayer`, opt-in with the *Game capture* switch in the settings) copies each presented image into exported DMA-BUFs and sends them over `/tmp/vesper-<uid>/capture.sock` to `vesper-gamecapture`. The socket is in `/tmp`, not `$XDG_RUNTIME_DIR`, because Proton games run inside the Steam Linux Runtime container (pressure-vessel). That container replaces `$XDG_RUNTIME_DIR` with its own tmpfs but shares the host's `/tmp`. Game only, at the game's frame rate, no portal.
2. **Conversion**: RGB to NV12 on the GPU (VA-VPP).
3. **Encoding**: VAAPI hardware encode (AV1 / HEVC / H.264). Prototype with `cros-codecs`, fall back to `ffmpeg-next`.
4. **Audio**: up to 8 PipeWire tracks (desktop, microphone, a device by node name, or an application's streams, followed as they come and go), each its own named Opus track, plus an optional mix of them all as the first track. Volume and mute per track, applied live. Per-track level meters in dBFS (sample peak, 20 dB per 300 ms release, 1.5 s peak hold, a clip light latched until clicked, left and right bars for stereo sources); they stop polling once silent or when the window is hidden, minimized or covered, and the next sound wakes them. Built-in filters per track (`vesper-dsp`) run on the track's encode thread, never on PipeWire's real-time thread: parameter changes are lock-free, a new filter list is built off that thread and handed over without a lock or an allocation. A filter's delay (noise suppression 20 ms, limiter lookahead) is removed from the track's timeline, so tracks stay in sync with the video and with each other. The mix goes through a true-peak limiter (-1 dBTP). Voice ducking: a track set to *Lower when I speak* is turned down (light, medium or strong: 6, 12 or 20 dB, 50 ms down, 300 ms hold, 600 ms back up) while a microphone track is heard, after its filters, volume and mute; *Background music* levels a track to a short-term loudness well under the voice (-30, -26 or -22 LUFS over 3 s), tames its peaks, dips the voice presence band (-4 dB around 2 kHz) and ducks it by 6 dB. Both run on the track's encode thread before its volume, so the track's own file and the mix get the same; the microphone and the tracks meet through one atomic timestamp (`VoiceKey`), no lock, no added latency. VST3 effects run in the same chains, each in its own host process (see *VST3 plugins*).
5. **Container**: MKV (crash-safe), optional remux to MP4.
6. **Live streaming**: FLV over RTMP/RTMPS or MPEG-TS over SRT (libavformat) from its own thread, next to the recording and the replay buffer. See [Live streaming](#live-streaming).

## Game capture layer: what it does when installed

Installing is an explicit opt-in: the *Game capture (Vulkan layer)* switch in Vesper's settings (or `crates/vesper-vklayer/install.sh`) copies the layer to `~/.local/share/vesper/` (`libvesper_vklayer.so`, and `libvesper_vklayer32.so` when the 32-bit build exists) and writes one manifest per architecture to `~/.local/share/vulkan/implicit_layer.d/` (`vesper_capture_64.json`, `vesper_capture_32.json`; the Vulkan loader picks by `library_arch`); turning the switch off (or `install.sh --uninstall`) removes them all, and the single `vesper_capture.json` of older versions too. Vesper never installs it otherwise; when the installed layer differs from the one built with Vesper (release builds, or a 32-bit layer added), the switch offers an Update button. Once installed, the layer loads into **every Vulkan app** of the user, 64-bit and now also 32-bit ones (when the 32-bit layer is installed), not only games. While Vesper is not recording it stays a pass-through, but it is not invisible:

- It adds `TRANSFER_SRC` to swapchain image usage (only when the surface supports it) and enables the export extensions the driver lists (`VK_KHR_external_memory_fd`, `VK_EXT_external_memory_dma_buf`, `VK_KHR_external_semaphore_fd`, `VK_EXT_image_drm_format_modifier` and their dependencies). If the driver rejects either change, the app's original request is retried unchanged.
- After the first capturable swapchain (640x360 or larger), it starts one background thread that tries to connect to Vesper once per second.
- No GPU memory is allocated and no frame is copied until Vesper selects the game. Vesper only captures Steam games (`SteamAppId` set) and games the user allowed; it identifies them through the kernel (`SO_PEERCRED`), same user only.

In the app, pick *Game* in the source card. It shows the captured game (or *Waiting for a game…*) and lets you switch to another running game. A non-Steam game asks first: *Allow Vesper to capture <name>?* Allow adds the name to the allow list (`allow_game=` lines in `~/.config/vesper/settings`), Ignore skips it until Vesper restarts. Games only copy frames while Vesper records or runs the replay buffer. While nothing records, a new game size that lasts over a second reopens the encoder at that size (the replay buffer restarts); during a recording the file keeps its size and the game is scaled to fit on the GPU, with black bars. A recording that gets no frame within 5 s (the game quit) fails instead of waiting.

Consent prevents accidental captures (a launcher, a tool, the wrong window). It is not a barrier against malicious code running under your account: with the layer installed, any process of this account can serve the socket and read Vulkan apps' frames without a portal prompt. The socket's directory must belong to you with mode 0700 and must not be a symlink. Vesper checks this and refuses to start game capture otherwise, with an error naming the directory. Another local user who creates `/tmp/vesper-<uid>` first can therefore block game capture, but cannot read frames. On top of that, both ends check the peer's uid (`SO_PEERCRED`). Flatpak apps get a private `/tmp`, so they cannot reach the socket unless granted host `/tmp` access (`--filesystem=/tmp` or `--filesystem=host`). An abstract socket was avoided for this reason: every Flatpak with network access shares that namespace. The allow list is keyed on the process name as the kernel reports it (`/proc/<pid>/comm`, 15 characters), so never allow generic names such as `java`, `python3`, `game.exe` or `launcher.exe`; keying on the executable path is a follow-up.

Escape hatches: a built-in blocklist keeps compositors, browsers, Electron apps, Steam, gamescope, OBS and Vesper itself a pure pass-through; `VESPER_CAPTURE_DISABLE=1` (e.g. `VESPER_CAPTURE_DISABLE=1 %command%` in Steam) stops the loader from loading the layer for one launch; the settings switch (or `install.sh --uninstall`) removes it.

Risks and limits: anti-cheats (VAC, EAC, BattlEye) may flag or reject unknown Vulkan layers, so use the escape hatches for those games. HDR output is not captured. The 32-bit layer exists only if it was built (see *Install*).

### Without the layer: the game window

When game mode needs a source and no game is captured by the layer or `vesper-gl` (the layer is off, a native OpenGL game without `vesper-gl`, a game it cannot capture), Vesper captures the game's window through the ScreenCast portal, windows only. The source card says how the game is captured: *Game (Vulkan)*, *Game (OpenGL)* (from the capture library loaded in the game), or *Game window*. The portal only asks when something needs it: a recording or a stream you start (after 2 s, so a layer game starting with it connects first), or the replay buffer while a Steam game has been running for 10 s (never while no game runs). KDE's picker shows once per game: its restore token is kept per game in `~/.config/vesper/window-tokens` (mode 0600), keyed by the game's Steam id (`SteamAppId`, else `SteamGameId` for a non-Steam shortcut, read from the environment of the user's processes: no game is connected to tell its name, the portal names no app, and unlike a process name it never mixes two Proton games); games outside Steam share one token. A token the portal refuses is replaced once the picker asks again; a D-Bus failure keeps it. A game waiting for *Allow* holds the picker back (its prompt shows instead). A cancelled picker, or a window that closes, is not asked again for that game until another game runs or you start a recording or a stream: never a picker in a loop.

A layer game always wins: when one is captured, the window capture stops (a picker still open is closed with its portal session); when it disconnects while its process still runs for 2 s more, its window takes over 2 s later, without stopping the recording: the last picture repeats meanwhile, and a size change is scaled to the file's size on the GPU, as for a resized game. Its process is watched until its window is captured: if it exits first, the recording stops and its window is not asked for (a picker already open is closed). A game that quits stops the recording as before, and so does the captured window closing. The window goes through the compositor, so the layer (or `vesper-gl`) stays the better choice: no compositor in between, the game's own frame rate.

### Native OpenGL games

OpenGL has no layer mechanism, so for the best performance in OpenGL games (Terraria and many FNA/SDL/GLFW indie games, emulators), add `vesper-gl` to the game's launch options in Steam (Properties > General); otherwise Vesper captures the game window (see above):

```
vesper-gl %command%
```

`vesper-gl` (installed in `/usr/bin` by the package) preloads `libvesper_glcapture.so` into that game only, the 64-bit or 32-bit build as the dynamic linker picks (`/usr/$LIB/vesper/`, that is `/usr/lib/vesper/` or `/usr/lib32/vesper/`; with a manual install, `<prefix>/bin/vesper-gl` looks in `<prefix>/lib/vesper/` and `<prefix>/lib32/vesper/`). Nothing is ever preloaded globally, and the settings switch is not needed. For a game outside Steam: `vesper-gl ./game`. The preload reaches every process the game's command starts, not only the game: launcher scripts (needed: Terraria starts through one), crash handlers, embedded browser helpers. They stay dormant pass-throughs (no OpenGL swap, or blocklisted), but they do load the library.

**Don't use `vesper-gl` on multiplayer games protected by VAC, EAC or BattlEye: risk of an account ban.** Anti-cheats treat preloaded libraries that hook OpenGL as cheats.

The library interposes `glXSwapBuffers`, `eglSwapBuffers` (and its `WithDamage` variants), and `dlsym`, `glXGetProcAddress(ARB)` and `eglGetProcAddress`, which is how SDL and GLFW find the swap functions after loading OpenGL themselves; every other lookup goes to glibc with the caller's own scope. Same protocol, consent, blocklist and pacing as the Vulkan layer: until Vesper selects the game, a swap costs an atomic load. While recording, the selected context's back buffer is blitted (flipped, GL being bottom-up) into a ring of 4 linear GBM buffers on the game's GPU, imported into its context as GL memory objects (`GL_EXT_memory_object_fd`); the GL state the blit touches (framebuffer bindings, read buffer, scissor test, sRGB writes) is restored. Each frame goes out with a sync_file from a DRM syncobj that the driver signals when the blit is done (`GL_EXT_semaphore_fd`), once the driver has submitted the blit (checked without waiting: Mesa has submitted it by then; otherwise the frame goes out on the next swap). Any failure turns capture off for that context and passes everything through. Measured in the lab (`scripts/robustness/l4_gl_32bit.sh`, uncapped test app at about 50 000 swaps/s): dormant within noise of no library at all, about 6 µs more per swap while recording at 60 fps; `l5_gl_block.sh`: Vesper stopped or killed mid-recording never blocks the game.

Limits: Mesa drivers only (importing a DMA-BUF and a DRM syncobj as opaque fds is Mesa behaviour; NVIDIA and others pass through), GL 3.0 / ES 3.0 or newer with `GL_EXT_memory_object_fd` and `GL_EXT_semaphore_fd`; one context per game is captured (the first to swap a window of 640x360 or more; another one takes over after it stops swapping for 2 s); multisampled windows (an MSAA default framebuffer) are not captured; `glXSwapBuffersMscOML` is not hooked. Games inside a Steam Linux Runtime container (pressure-vessel) get the preload only if the container honours `$LIB` in `LD_PRELOAD`; Terraria (native) runs outside of it. 

## Done

- Record a screen, a window or a game (Vulkan layer, 64 and 32-bit; native OpenGL games with `vesper-gl`), constant frame rate, AV1 / HEVC / H.264 with constant-quality presets.
- Up to 8 named audio tracks (desktop, mic, devices, applications) with volume and mute, plus a mix track, sample-aligned and drift-corrected. The desktop and microphone devices are chosen in the settings (system default or a specific device, never silently replaced when unplugged), and any track's source can be changed after it was added.
- Built-in filters per track (noise suppression, expander, compressor, de-esser, limiter, high-pass, gain), changed live, with a one-click voice preset and gain reduction meters.
- VST3 effects per track, hosted out of process: a plugin that crashes or stalls leaves its track dry, never the recording down.
- Global hotkeys (GlobalShortcuts portal).
- Replay buffer: ring buffer of encoded packets, save the last N seconds.
- Slint UI, tray icon, start with the session.
- Live streaming to Twitch, YouTube or any RTMP/RTMPS/SRT server, at the same time as a recording and the replay buffer.

## Install

Global shortcuts need an app id, and the portal only accepts one with an installed desktop file whose `Exec` binary it can find.

Arch (and CachyOS): the package builds the last commit of this checkout (uncommitted changes are left out), no GitHub access needed:

```sh
cd packaging/arch && makepkg -si
```

It installs `/usr/bin/vesper`, `/usr/bin/vesper-gl`, the desktop file, the icons (app and tray), and the game capture layer, the OpenGL capture library and the VST3 plugin host (`vesper-vst-host`) in `/usr/lib/vesper/`, plus the 32-bit layer and OpenGL library in `/usr/lib32/vesper/` when the build machine has the i686 Rust target and a 32-bit C toolchain: `rustup target add i686-unknown-linux-gnu` (no root; or `pacman -S lib32-rust-libs` with Arch's `rust`) and `pacman -S lib32-glibc lib32-gcc-libs` (multilib repository). Without them the package builds without 32-bit game capture. 32-bit Vulkan games also need `lib32-vulkan-icd-loader` and a 32-bit Vulkan driver (`lib32-vulkan-radeon`), which Steam installs anyway. The layer stays off: only the settings switch enables it, per user. Uninstall with `sudo pacman -R vesper-git`. Turn the switch off first: otherwise your per-user copy of the layer stays installed and keeps loading into Vulkan apps; remove it by hand with `rm ~/.local/share/vulkan/implicit_layer.d/vesper_capture*.json ~/.local/share/vesper/libvesper_vklayer*.so`. Each `makepkg` rewrites `pkgver=` in the PKGBUILD (normal for a -git package): `git checkout packaging/arch/PKGBUILD` before committing.

Manual alternative, in your home:

```sh
cargo build --release
install -Dm755 target/release/vesper ~/.local/bin/vesper
install -Dm644 target/release/libvesper_vklayer.so ~/.local/lib/vesper/libvesper_vklayer.so
install -Dm755 target/release/vesper-vst-host ~/.local/lib/vesper/vesper-vst-host
install -Dm644 target/release/libvesper_glcapture.so ~/.local/lib/vesper/libvesper_glcapture.so
install -Dm755 crates/vesper-glcapture/vesper-gl ~/.local/bin/vesper-gl
# 32-bit games (optional): rustup target add i686-unknown-linux-gnu, lib32-glibc, lib32-gcc-libs
cargo build --release --target i686-unknown-linux-gnu -p vesper-vklayer -p vesper-glcapture
install -Dm644 target/i686-unknown-linux-gnu/release/libvesper_vklayer.so ~/.local/lib32/vesper/libvesper_vklayer.so
install -Dm644 target/i686-unknown-linux-gnu/release/libvesper_glcapture.so ~/.local/lib32/vesper/libvesper_glcapture.so
install -Dm644 crates/vesper-app/data/io.github.PaulCarouge.Vesper.desktop -t ~/.local/share/applications/
mkdir -p ~/.local/share/icons && cp -r crates/vesper-app/data/icons/hicolor ~/.local/share/icons/
```

Vesper looks for the layer and the plugin host next to its binary, then in `../lib/vesper/` (the 32-bit layer in `../lib32/vesper/`, or `target/i686-unknown-linux-gnu/<profile>/` for a build in the checkout); the settings switch installs that copy (build with `cargo build --release` at the workspace root, not `-p vesper-app`, so the layer is built too). If `~/.local/bin` is not in the session `PATH`, set `Exec=` to the full path. Without the desktop file, global shortcuts and desktop notifications (sent when a recording or replay is saved, or fails, while the window is in the background) are off; the in-window shortcuts still work. The saved source is forgotten once after updating to this version, since it is now tied to the app id: pick it again. Default global shortcuts: Alt+F9 starts or stops recording, Alt+F10 saves the replay, Alt+F8 goes live or ends the stream. KDE asks to confirm them on first launch; change them later in System Settings > Shortcuts.

Settings are kept in `~/.config/vesper/settings`.

**Profiles** are named sets of recording settings, switched from the picker in the window's header (e.g. "Game — 1440p144 AV1" and "Desktop — 60 fps HEVC"). A profile holds the source mode (screen or game), codec, quality, frame rate, replay buffer (on/off and length), audio tracks (sources, volumes, mute, filters, VST3 plugins), the desktop and microphone devices, the mix track, the output folder and the stream settings (service, URL, resolution, frame rate, bitrate, encoder). The stream key is never in a profile: each service keeps its own in the keyring (see *Stream key* below), so a profile on another service never gets it. The app's own settings (autostart, game capture layer, allowed games, shortcuts, theme) are shared by all profiles. Each profile is `~/.config/vesper/profiles/<name>.conf` (same `key=value` format, mode 0600); `settings` names the current one (when it names none or a missing one: *Default*, else the first by name). On first launch, a version without profiles copies `settings` to `~/.config/vesper/settings.pre-profiles`, then moves its recording settings into a *Default* profile, each step synced to disk. A settings file or profiles folder that cannot be read is never migrated or overwritten: Vesper starts with the defaults, says so, and saves nothing until restarted. Going back to an older Vesper: it starts from its defaults (the recording settings are now in the profiles); copy `settings.pre-profiles` over `settings` to get the old ones back. Changes save into the current profile. The menu creates a profile (default settings), duplicates the current one (its VST3 plugins get copies of their state under new ids, so profiles never share one), renames it, or deletes it after a confirmation (with its plugin states; never the last profile). Switching applies everything at once: audio and replay changes go to the running replay buffer, another source mode or video encoding restarts it. It is locked while recording or streaming.

**Scenes** stack layers on the recorded canvas: the capture, PNG/JPEG images, text (font, colour, outline, shadow) and webcams (by PipeWire `node.name`). The scene editor (the layers button in the header, or *Edit* on the scene chips) lists the profile's scenes (new, duplicate, rename, delete), shows the edited scene on a preview where layers are moved and resized with the mouse (edges and centres snap to the canvas and to the other layers; Shift keeps a corner's proportions, Ctrl places freely), lists its layers top first (show or hide, reorder, remove; add the capture, an image picked through the file portal, text, or a webcam found on PipeWire) and sets the selected one: opacity, fit (contain, cover, stretch) and crop, plus the text's content, font (the system's families), size, colour, outline and shadow. The canvas is automatic (the capture's size) or fixed (1080p, 1440p, 2160p or any size); changing it restarts the replay buffer, and it is locked while recording or streaming. Every other change is saved in the profile and, for the recorded scene, applies at once, also while recording or streaming. The preview draws the layers itself (images and text rasterized on a helper thread, stand-ins for the capture and webcams); while it shows the recorded scene with overlays, the window is visible and the pipeline runs, it shows the composed picture instead: a 480 x 270 copy about 10 times a second, read back from the GPU only then (never otherwise, never on the encode path). With scenes, chips under the source card (with a *Camera on* mark while a webcam streams) switch the recorded scene with a click, also while recording or streaming; so do the tray's *Scene* menu and the global shortcuts *Next scene* and *Scene 1* to *Scene 4* (unbound until you bind them in System Settings > Shortcuts). In a profile: `canvas=auto` (the capture's first size, as before) or `canvas=2560x1440` (fixed, kept while recording; lets a scene without the capture, e.g. *Be right back*, record before any frame), `scene_active=<name>`, `scenes=`, then `scene=<name>` and its `layer=kind|visible|opacity|x,y,w,h|left,top,right,bottom|contain/cover/stretch[|path, node or style|text]` lines, bottom first (rect in canvas fractions, crop in source fractions; the last value escapes `\\`, `\n` and `\r`). At most 16 scenes of 16 layers; invalid lines are ignored. A profile without scenes records the capture alone, exactly as before: frames go straight to the encoder and no Vulkan device is created. Otherwise `vesper-compose` draws the scene on the GPU only when the capture or an overlay changed. Images are decoded, text rasterized and textures staged on a helper thread, which also creates the compositor and keeps it 10 s after leaving a composed scene. Capture frames go back to their producer as soon as the GPU has read them. An overlay change with no new frame is drawn from a copy of the last one for portal sources, which send frames on damage only; a game's redraw waits for its next frame (the copy would cost about 0.07 ms of GPU per 4K frame). The tick never waits more than half a frame for a composition: a GPU busy with a game repeats the last picture rather than stalling the recording. The active scene can change while recording or streaming (same file, same size). If the compositor fails, the capture alone is recorded, a notice says so, and the compositor is retried with a backoff (2 s doubling to 60 s): an overlay never ends a recording. A webcam opens as soon as the pipeline runs (replay buffer included) with a scene that shows it, stays open 10 s after leaving that scene and closes with the pipeline; the UI is told when one streams (`Event::Camera`). Its latest picture (decoded by the GPU, or raw YUY2/NV12 converted to RGB in a shader with the camera's matrix and range) is copied into the compositor's own image by the next composition and released at once. An unplugged or failing webcam is hidden with one notice and reopened with a backoff (1 s doubling to 10 s); the recording goes on. A 1080p30 MJPEG webcam on a 1440p canvas costs about 0.085 ms of GPU per composition (camera copy included; the JPEG engine's own time aside) and under 1 % of a core (lab, debug build).

The icons (`crates/vesper-app/data/icons/`) come from `scripts/icons.py`: edit it and run `python3 scripts/icons.py` (needs `rsvg-convert`) to regenerate the SVGs and PNGs. Preview: `docs/screenshots/icons.png`.

The scene compositor's compute shader (`crates/vesper-compose/shaders/compose.comp`) is committed with its SPIR-V (`compose.spv`), so building needs no shader compiler. After editing it, run `scripts/shaders.sh` (needs `glslc` from shaderc or `glslangValidator` from glslang; checks the result with `spirv-val` when installed) and commit both files.

Failure-injection lab (disk full, game crash, portal or PipeWire gone...): `scripts/robustness/go <name> <scenario>.sh` runs a scenario against a debug build in a private user/mount/pid namespace with its own D-Bus, PipeWire (no real device) and headless gamescope; see `scripts/robustness/run.sh`. The real session's sockets (`/run/user`) are hidden and the bus starts with the lab's `HOME` and XDG directories, so the services it activates (portal, kwalletd, permission store) never reach the real compositor, wallet or files. `w1_window_fallback.sh`: a Steam game without the layer and a recording ask the (absent) portal for its window once, never in a loop. `c1_camera.sh`: the webcam source against fake camera nodes (MJPEG decoded on the GPU, raw YUY2, unplugged mid-stream, a missing camera); build `cargo build -p vesper-capture --example camera_lab` first. `c2_camera_scene.sh <test binary>`: a webcam layer through the whole pipeline against the fake node, colour checked in the file, cost printed.

## VST3 plugins

*Add filter* lists the VST3 effects installed in `~/.vst3`, `/usr/lib/vst3` and `/usr/local/lib/vst3` (vendor sub-folders included), after the built-in filters. They are enabled, removed and reordered like the built-in ones, and changed live while recording.

- **Out of process.** Each plugin instance runs in its own `vesper-vst-host` process. Audio goes through shared memory: the track's encode thread hands each 20 ms block to the host, wakes it with a futex and waits for the answer without allocating; all the plugins of a track share 8 ms per block. Control (load, parameters, state) goes over a Unix socket. If the host is late, still starting, crashed or was killed, or the plugin fails the block or outputs NaN or infinity, the block goes out dry, delayed by the plugin's latency so the track stays in place; the filter's title says *bypassed* with the reason. The host is restarted with a growing delay (0.5 s, doubling, up to 30 s; reset after 30 s of normal running), with the plugin's last saved state and the parameters set since. Three late blocks in a row count as a stall. A host also dies with Vesper, inherits none of its other files, cannot resize the shared audio region, and is the first process the kernel kills when memory runs out. The host binary is only taken from next to `vesper` or `../lib/vesper/`, never from `PATH`; without it, plugins show *not installed*.
- **Latency.** The latency a plugin reports (also when it changes it) is removed from the track's timeline like the built-in filters' (noise suppression, limiter lookahead): tracks stay in sync. Up to 1 s is followed; a plugin that reports more is bypassed.
- **Scanning** runs when *Add filter* opens, not at startup. Each bundle is opened by its own host process (10 s limit), so a plugin that crashes on load is only skipped. Results, failures included, are cached by the module's modification time in `~/.config/vesper/vst3/scan-cache`.
- **Settings.** The filter list in the profile's file (`~/.config/vesper/profiles/`) only holds `vst3:id=<n>`. The `vst3` folder is private (0700, files 0600) and ids are never reused. Each instance's plugin path, class id and state (component and controller, base64) are in `~/.config/vesper/vst3/<n>.conf`, saved when its settings are. Removing the filter, or its track, stops its host and deletes that file, as does deleting the profile; nothing else deletes it.
- **Parameters** are shown as generic sliders (0-100 % of the plugin's normalized range), the first eight in the card, the others behind *More settings*. Read-only, hidden and program-change parameters are left out.
- **Limits.** Effects with a mono or stereo main bus only (side-chain inputs get silence); 48 kHz, 32-bit float; no MIDI. No plugin editor window yet: plugin GUIs (X11 embedding through Xwayland, or Wayland) are a follow-up, as are plain-value parameter labels (`-6 dB` instead of a percentage) and parameter changes made inside a plugin's own GUI. A plugin that needs the host's `IMessage` objects to link its processor and controller may lose that link.

The host uses the `vst3` crate (bindings generated from the VST3 SDK headers, MIT or Apache-2.0); the VST3 SDK itself is MIT-licensed since version 3.8.

## Live streaming

*Go live* (the Live stream card, Ctrl+L, the tray menu, or the global shortcut Alt+F8) streams what Vesper captures; recording and the replay buffer keep running beside it. The *Live stream* settings choose:

- **Service**: Twitch goes to its automatic ingest, `rtmps://ingest.global-contribute.live-video.net/app` (the "Default" entry of `https://ingest.twitch.tv/ingests`, which replaced `live.twitch.tv`); YouTube to `rtmps://a.rtmps.youtube.com:443/live2` (`rtmp://a.rtmp.youtube.com/live2` in clear). Both over TLS, with the server's certificate and host name checked (`tls_verify=1`; a libavformat older than 62 is refused for `rtmps://`, and a TLS layer that does not take the option fails closed), so the key does not cross the network in clear. *Custom* takes an `rtmp://`, `rtmps://` or `srt://` URL: the key becomes the last path segment for RTMP, the `streamid` for SRT (or, written `streamid=...&passphrase=...`, both SRT parameters). The settings warn that `rtmp://` sends the key in clear and that `srt://` is encrypted only with a passphrase. A key pasted into the URL (an RTMP path below the application, an SRT `streamid` or `passphrase`) is moved to the key field and never written to the settings file. Only the network protocols a stream needs are allowed (`rtmp,rtmps,tls,tcp,srt`).
- **Resolution** (native, or fit in 1080p or 720p, never upscaled), **frame rate** (30 or 60), **bitrate** (1 to 20 Mbit/s, constant bitrate with a 1 s buffer) and **encoder**. Twitch gets H.264: its HEVC/AV1 "Enhanced Broadcasting" is limited to OBS with NVIDIA GPUs. YouTube and custom servers can also take HEVC or AV1 (Enhanced RTMP over RTMP, plain MPEG-TS over SRT).
- **Stream key**: one per service: Twitch, YouTube, and each custom server host (`custom:<host>`, without port or user). A key is only ever sent to the service it was saved for: switching service (or profile) shows that service's key, or asks for one. Kept by the Secret Service (`org.freedesktop.secrets`: KWallet on Plasma, GNOME Keyring, KeePassXC; attributes `application`, `type=stream-key`, `service`), encrypted at rest and unlocked with the session; Vesper never writes it to its settings file or its logs, and only shows where it is kept. The Secret portal is meant for sandboxed apps and would leave the encryption to Vesper, so it is not used. Only when the session has no Secret Service at all (or no default keyring) do the keys go to `~/.config/vesper/stream-keys` (one `<service>\t<key>` line each), written atomically with mode 0600 like the portal restore token: private to your account, but in clear on disk. The single key of earlier versions only ever goes to the service it was saved for: the one selected in those settings (`settings.pre-profiles`). It moves (into the keyring when there is one, else into `stream-keys`, synced to disk) and the old item or file is deleted only once the new copy reads back equal. When that service already has a key, or the keyring stays locked, or the service cannot be told, the old key is left untouched. A keyring that is there but stays locked (prompt dismissed) gets *The keyring stayed locked: key not saved*, never a copy in clear. The settings file itself is written with mode 0600.

How it is encoded: the stream is a second VAAPI encode of the same NV12 picture, scaled on the GPU (VA-VPP), with its own codec, size, rate control and a keyframe every 2 s; nothing is captured or converted twice. When the stream asks for what the recording already makes (same codec, size and frame rate, and the recording's bitrate cap within the stream's bitrate), it sends the recording's packets instead, with no second encode. The stream's encoder is opened on a helper thread, never on the tick; if it cannot keep up (each stream frame taking longer than a frame for a second), the stream ends with *The GPU encoder is overloaded* so the recording stays smooth. When the recording's encode is shared, a keyframe is forced into the recording only when the stream (re)connects, never on congestion. Audio is the mix of the recorded tracks (the same mix and limiter as the mix track), encoded to AAC-LC at 160 kbit/s for the stream only; the Opus tracks of the files are untouched. When neither the files nor a stream use the mix, it is idle: its inputs drop their samples without taking its lock, and it lines them up again on the shared timeline when a stream starts. Without any audio track, the stream is silent and a notice says so. Measured on the RX 9070 with a 1440p60 game recorded in HEVC: recording alone 2.2 % of a CPU core and 42 % of the VCN encoder; with a 1080p60 6 Mbit/s H.264 stream 3.9 % and 64 %; sharing the recording's encode 3.7 % and 42 % (`scripts/robustness/t5_cost.sh`).

The network never slows capture, encoding or the recording: the pipeline only queues packets for the `vesper-live` thread. When more than a second of video waits (the uplink is slower than the bitrate), the waiting video is dropped, and new video up to the next keyframe, which the stream encoder makes at once; the card shows the bitrate sent and the frames dropped. A lost connection is retried after 1, 2, 4... up to 30 s (*Reconnecting*), the recording going on meanwhile. A server that refuses the connection, rejects the stream, or closes it three times in a row right after it started ends the stream with what to check (server URL, stream key); an unreachable server (no network) is retried, an unknown host three times. Host names are resolved on a throwaway thread, so ending the stream never waits for DNS. An SRT server that does not answer is reported as unreachable, never as a wrong key.

Limits: no adaptive bitrate (a slow uplink drops frames rather than lowering the quality); one stream at a time; a stream frame rate below the recording's sends the latest recorded picture of each stream frame; the stream keeps the size the recording's encoder opened at (a resized game is fitted with bars, as in a recording); whether the stream has audio is decided when it starts (tracks turned on or off later do not change it); a custom server URL is saved in the settings file as typed, so put the key in the key field, not in the URL.

Tested without any real service, in the failure-injection lab (private network namespace, loopback only): `t1_stream.sh` (a game streamed to `ffmpeg -listen` while recording, checked with ffprobe: codec, size, frame rate, 2 s keyframes, AAC, audio and video spans; `PROTO=srt`, `CODEC=hevc|av1`, `H=0` for the shared encode), `t2_reconnect.sh` (the server killed mid-stream and back 6 s later), `t3_throttle.sh` (the loopback limited to 3 Mbit/s with `tc`), `t4_rejected.sh` (a server hanging up after the handshake, a wrong port, an unknown host), `t5_cost.sh`, `t6_shots.sh` (screenshots with demo data) and `t7_idle_mix.sh` (audio thread CPU with an idle mix). The TLS checks are unit tests against `openssl s_server` with a self-signed certificate, a trusted CA's certificate for another host, and one for the right host. `scripts/fake_secret_service.py` is an in-memory Secret Service for the keyring tests on a private bus (`DISMISS=1` refuses the unlock prompt).

## Background and tray

Vesper shows an icon in the system tray (StatusNotifierItem, as on KDE Plasma). A left click shows or hides the window; its menu starts or stops a recording, saves the replay (while the replay buffer runs), goes live or ends the stream, turns the replay buffer on or off, and quits. Its icon follows the panel's colors and shows the state: a loop while the replay buffer runs, a red dot while recording, waves while live.

With a tray, closing the window keeps Vesper running in the background, with the replay buffer and global shortcuts; the first time, a notification says so. Quit from the tray menu or with Ctrl+Q in the window (logging out, SIGTERM or SIGINT quit the same way): a recording in progress and replays being saved are finished first. Without a tray (no StatusNotifierWatcher on the session bus), closing the window quits, as before. Only one Vesper runs per session: launching it again shows the running one's window (it owns the D-Bus name `io.github.PaulCarouge.Vesper`). While the window is hidden, messages such as *No game to record yet* come as notifications.

*Start with the session* in the settings (off by default) writes `~/.config/autostart/io.github.PaulCarouge.Vesper.desktop` (under `$XDG_CONFIG_HOME` if set), which runs `vesper --background`; turning it off removes the file. `--background` starts with the window hidden in the tray (shown anyway when there is no tray), and the replay buffer starts if it is on in the settings.

## Roadmap

Every feature below must keep recording quality, game performance and compatibility intact: nothing on the game's render path, compositing and encoding on the GPU, audio processing off the PipeWire real-time thread.

1. **VST3 plugin editors**: the plugins' own windows, next to the generic sliders.
2. **Scenes and profiles**: sources composited on the GPU (VA-VPP / Vulkan) into the encoded picture, saved per profile.
3. **Overlays**: images, text, webcam, and optional browser sources, on the same GPU compositor.

Not planned: plugin APIs for the video pipeline itself.

## Known risks

- Wayland delivers frames on damage only: constant framerate needs frame duplication or timestamp handling.
- DMA-BUF modifier negotiation between PipeWire and VAAPI.
- Hybrid GPUs: pick the right render node explicitly.
